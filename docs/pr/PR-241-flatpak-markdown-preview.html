Markdown preview (Ctrl+M) opens in the browser inside the Flatpak

Before · In the FlatPark Flatpak, View → Preview in Browser (Ctrl+M) on a Markdown file did nothing: no browser, no error.
After · Ctrl+M opens GNOME's "Open With" chooser and then the browser, which shows the rendered page. Saving the file rewrites the page, and a browser reload shows the edit.

The user found it on 2026-11-27 with FlatPark 0.9.10 on GNOME, while checking T0118's app-page text with the orchestrator. FerrisPad wrote the preview to the sandbox's private /tmp, and the host browser cannot read it through the OpenURI portal. The fix stays reactive: it changes only where the file is written, and adds no watcher or timer.

  • In a Flatpak, the preview goes to $XDG_CACHE_HOME/ferrispad_preview, which is ~/.var/app/com.ferrispad.FerrisPad/cache/ferrispad_preview, the same path on the host.
  • Outside a Flatpak nothing moves: it stays in /tmp/ferrispad_preview.
  • On Linux and macOS, the preview folder must be a real folder owned by the user, and it is made private (0700). A symlinked or foreign folder is refused. This fixes a pre-existing security issue that a3 found in review.
  • Flatpak detection is unchanged: the updater's /.flatpak-info check.
  • At startup, preview files older than 24 h are swept from the preview folder. Before, the leftovers of a crash were never removed.

How the preview reaches the browser, now

Ctrl+M · PreviewController renders the Markdown and writes preview_<hash>.html into the folder it chose at startup.
Folder · In a Flatpak with a cache dir, <cache>/ferrispad_preview; otherwise <temp>/ferrispad_preview, as before. On Linux and macOS, before each write: created if needed, then it must be a real folder owned by the user, and it is set to 0700. Otherwise the preview is refused.
Open · open::that runs xdg-open. In the sandbox that is flatpak-xdg-open, which goes through the OpenURI portal. The host browser can read the cache path, but not the sandbox's /tmp.
Save · Saving a Markdown file rewrites the same preview file. There is no new open; the user reloads the tab.
Quit · The session's preview files are removed, then the folder if it is empty.
Next start · Preview files older than 24 h are removed once: what a crashed or killed run left behind. Newer ones stay.

T0119: the Flatpak preview goes where the browser can read it

Before · Ctrl+M in the Flatpak wrote /tmp/ferrispad_preview/… inside the sandbox and handed it to the portal. Nothing opened, and nothing said why.
After · The file is written under the app's cache dir. Inside the sandbox, xdg-open of that path opens the chooser and then the browser.

The orchestrator reproduced it with the user inside the installed sandbox:

  • xdg-open /tmp/test1-tmp.html exited 0 and did nothing else: no chooser and no portal log.
  • The same page under $XDG_CACHE_HOME/ferrispad_preview/ opened GNOME's chooser, then the browser on file:///home/…/.var/app/com.ferrispad.FerrisPad/cache/ferrispad_preview/test2-cache.html.

The orchestrator then specified the fix: the cache dir in a Flatpak, created 0700, with cleanup working in both places. a3's review of the first version, as decided by the orchestrator, kept the Flatpak check as it was and added the folder checks.

  • Flatpak check: the preview calls updater::is_flatpak(), which looks only at /.flatpak-info. updater.rs has no diff against master.
  • preview_dir_for(in_flatpak, cache_dir, temp_dir): a pure chooser. PreviewController calls it once in new() and stores the result. Writing, refreshing on save and cleanup all use that stored folder, so they cannot point at different places.
  • prepare_preview_dir (Unix): it runs before every write and before the sweep.
    • It creates the folder (0700) if it is missing.
    • It checks with symlink_metadata that the folder is a real directory and not a symlink.
    • It checks that the folder is owned by the effective user, using geteuid from the nix crate.
    • It sets mode 0700.
    If a check fails, the write returns the existing "Failed to write preview file" notice, and nothing is written or swept. nix 0.28 is already built for portable-pty, so no new crate is added: Cargo.toml only turns on its user feature. On Windows nothing changes: %TEMP% is per user.
  • Startup sweep (added to the ticket by the user's decision, 2026-11-27): sweep_stale_previews runs once in PreviewController::new(), with no timer and no thread.
    • It removes regular files named preview_<16 hex>.html, directly inside the preview folder, whose mtime is older than 24 h.
    • It does not recurse into subfolders, skips symlinks without following them (symlink_metadata), and never touches anything outside the folder.
    • Any read or remove error is ignored.
    Before, cleanup ran only on a normal exit. A crash left its previews behind for good in Windows %TEMP% and in the Flatpak cache dir, which nothing clears.
  • Testable write: open_in_browser is now write_preview (write and track) followed by open::that. The cleanup test therefore runs without launching a browser.

No visible change in FerrisPad's own windows: the menus, dialogs and editor are identical. The change is in which file the host browser receives. shoot.sh cannot show that: it shims xdg-open to fail by design, and it does not run inside the Flatpak. The defect, red first. Today's preview_dir() was first moved behind the pure function, unchanged, so the test compiled. preview_dir_in_flatpak_uses_the_cache_dir then failed with left: "/t/ferrispad_preview", right: "/c/ferrispad_preview". The guard preview_dir_outside_flatpak_is_unchanged passed before and after. For the sweep, with an empty stub, sweep_removes_only_old_preview_files failed with an old preview file is removed.
Pre-existing security issue, found by a3. FerrisPad used /tmp/ferrispad_preview as it found it. Another local user could create that folder first, or plant a symlink there, and receive the previews or redirect the writes. Two tests are red on d8816a6:
  • existing_open_dir_is_made_private: a 0777 folder stays 0777 (left: 511, right: 448);
  • symlinked_preview_dir_is_refused: the write goes through the symlink.
Both pass now. A folder owned by another user cannot be created without root, so that check has no test.
Dropped after review: a wider Flatpak check. The first version also counted a non-empty FLATPAK_ID as a Flatpak, with a red test, flatpak_detection. That tested a heuristic, not the bug. A host process can inherit FLATPAK_ID, for example from VS Code's Flatpak, so the updater would have turned off for it. The heuristic is gone. The guard flatpak_id_alone_is_not_a_flatpak re-runs its own test binary with only FLATPAK_ID=com.visualstudio.code set, and expects no Flatpak. It failed on d8816a6 and passes now, as it does on master.
Why 24 hours, and only at startup. A newer file may belong to another FerrisPad window that is still running, so the sweep leaves it alone. Running once at startup keeps the 0% idle CPU rule: no timer, no watcher, no thread that lingers. The user approved this scope, relayed by the orchestrator.
Why the cache dir, and only in a Flatpak. The sandbox's $XDG_CACHE_HOME sits under ~/.var/app/<id>, which the host sees at the same path, so the portal can hand it to the browser. Outside the Flatpak the browser already reads /tmp, so moving that folder would change behaviour no one asked to change.
Why the checks apply to both folders. The shared /tmp is where a planted folder or symlink can come from. In the Flatpak cache dir, the same rule costs nothing. The browser runs as the same user, so 0700 does not stop it from reading the preview. The orchestrator put the checks in this ticket because they are in the same function as the folder choice, and the page already promised 0700.
Not fixed here.
  • The chooser is not attached to FerrisPad's window (the portal logs "Failed to associate portal window with parent window"), so it can open behind it.
  • open::that returns Ok once xdg-open has spawned, so a portal failure stays silent.
  • Outside a Flatpak the preview stays in /tmp/ferrispad_preview. A planted folder is now refused rather than used, but then the preview does not open, and a popup says why. Moving the folder out of /tmp would be a separate decision.

Release notes and compatibility

  • CHANGELOG: Fixed: in the Flatpak, Markdown preview in the browser (Ctrl+M) did nothing. The preview is now written to the app's cache folder, which the browser can read. Preview files left behind by a crash are removed at the next start, once they are older than a day.
  • Settings, session files, plugins and themes are untouched. If a user's /tmp/ferrispad_preview was created by someone else, or is a symlink, the preview is now refused with a popup instead of being written there. A preview left in the old sandbox /tmp by 0.9.10 is not carried over: that /tmp is private to each sandbox run.

End-to-end verification

A user of the installed FlatPark FerrisPad previews a Markdown file, edits it, and sees the edit in the browser. Run from the branch's worktree with a throwaway config and data directory, so the run never reads or writes your real Flatpak settings and sessions.

Starting state

  1. nix develop -c cargo build --release the release binary is in target/release/FerrisPad.
  2. S=$(mktemp -d -p $PWD) && mkdir $S/cfg $S/data, then write $S/notes.md with a heading, a list and ![img](pic.png), and put a pic.png next to it. The scratch dir is under the worktree because the sandbox does not see the host's /tmp. ls ~/.var/app/com.ferrispad.FerrisPad/cache/ shows no ferrispad_preview.
  3. flatpak run --filesystem=/nix:ro --env=XDG_CONFIG_HOME=$S/cfg --env=XDG_DATA_HOME=$S/data --command=$PWD/target/release/FerrisPad com.ferrispad.FerrisPad $S/notes.md FerrisPad opens notes.md. The scratch dirs reach only the sandbox (--env), so your shell and your real Flatpak settings are untouched. --filesystem=/nix:ro lets the Nix build load its libraries, for this run only; it is not a saved override.

The scenario

  1. Press Ctrl+M. The "Open With" chooser appears, possibly behind FerrisPad. Choose the browser: it shows the heading, the list and the image.
  2. Add a line to the Markdown and press Ctrl+S. Do not press Ctrl+M. Reloading the browser tab shows the new line.
  3. Add another line and press Ctrl+M. The page shows that line too, after the chooser if it asks again.
  4. Quit FerrisPad, then ls ~/.var/app/com.ferrispad.FerrisPad/cache/ No ferrispad_preview is left.
  5. Outside the Flatpak: nix develop -c cargo run --release -- $S/notes.md, then Ctrl+M. The browser opens the preview from /tmp/ferrispad_preview/, as before.
  6. rm -rf "$S" the scratch dirs are gone.
