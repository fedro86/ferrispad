Pull request #203 · ticket/T0101 → master · robustness

With several FerrisPad windows on one session, no unsaved text is lost, and a closed document stays closed

Before · Two FerrisPad instances share a session with restore on. One instance's save could drop the other's unsaved document and delete its temp file while it was running, so a crash then lost that text. A closed document could also come back, and two instances could end up writing one temp file.
After · Each session entry records the instance that owns it. A document leaves the session only when the instance that had it closes it. Unsaved text of another instance is always kept. A restored copy whose owner is still alive gets its own temp file.

The orchestrator assigned this as T0099's follow-up for 0.9.11. One case came from a3's T0099 review. The fix is in the session merge, which runs on saves that already happen: there is no new timer or watcher, so the 0% idle CPU rule holds.

  • A save never drops another live instance's document or its temp file.
  • A copy closed by an instance does not come back. A reopen of the same file in another instance survives.
  • No temp file has two writers: a restore forks the temp file unless its owner is gone.
  • The instance id is <pid>-<nonce>, so a reused pid never takes over a crashed instance's entries.
  • On Windows, a process that cannot be inspected (for example an elevated one) counts as alive.

How the session merge works, now

Owner · Every entry in session.json carries owner: the instance that wrote it as its own. An older file has no owner, so the file's instance_id stands in.
Memory · Each instance keeps, in memory, the identities it wrote in its last save and the copies it took over at restore. A copy it had and no longer has was closed, or renamed by Save As, by that instance.
Merge · This runs on every save, even when the file on disk is the instance's own.
  • The instance's current documents replace every entry it owns.
  • Another instance's entry stays, unless this instance closed that exact copy.
  • Unsaved text of another instance is always kept.
Restore · An entry's temp file is taken over only from an instance that is gone. When the owner is alive or unknown, the restored copy gets its own temp file.

T0101: a document leaves the session only when its instance closes it

Before · A's second save found its own session.json and skipped the merge. It wrote only A's documents and deleted B's temp file while B was running. If B was then killed, B's unsaved text was gone.
After · A's save keeps B's entry and B's temp file. Killing B afterwards loses nothing, and the next start restores B's text.

The ticket began with two reports of a closed document coming back. Neither reproduced through normal flows with two real instances on Xvfb. Reading the merge code then turned up three cases:

  • Data loss: the one above. It is pre-existing and was shown on Xvfb.
  • Resurrection: A merged B's document. B closed it and saved an empty list, and the "never clobber a foreign session" guard (T0015) made B write nothing. An instance started before A's next save restored the closed document. This case came from a3's T0099 review.
  • Shared temp file: B restored A's unsaved document while A ran. Since T0099 it reused A's temp file, so two live instances wrote one file and the last writer won.
  • No liveness test in the merge. Asking "is the other instance alive?" cannot tell "someone took over its documents" from "nobody has them". With that test, a crashed instance's unsaved text would be dropped. The merge uses ownership instead.
  • <pid>-<nonce> instance id. With a bare pid, a new process that got a crashed instance's pid would take that instance's entries for its own and drop them. The nonce is random per run and std-only. Liveness reads the pid prefix, and another run with our own pid is gone.
  • Windows fails safe. If OpenProcess fails with anything but "no such process", the process counts as alive. Its documents are kept and its temp file is forked.
  • The adoption fork rule was the orchestrator's decision. A duplicate tab on a later restore is accepted; a lost text is not.

Evidence redone: the first two-instance runs were invalid. The helper that found an instance's window ran xdotool search --pid P --name FerrisPad. xdotool ORs its search criteria, so both "A" and "B" resolved to the newest window, and every keystroke went to one process. With --all, A and B map to different windows. The tables above are the reruns, and their conclusions did not change. The unit tests never depended on the harness.
Why no tombstones. An ordered-tombstone variant, which persists a record of each close, was considered. The owner-scoped rule replaced it because it needs no clock. A close lost to a crash before the next save leaves the document in the session, which is the safe direction.
Known limitation: crashed instances' entries pile up. An entry whose owner crashed with unsaved text is kept. Only a restore that adopts it, followed by a close, removes it. In SavedFiles mode a restore never adopts temp entries, so each crash with unsaved text adds entries and temp files that stay. The ticket sketches a follow-up, "Recover documents from crashed sessions": at startup, offer such documents once, with Restore or Discard. It is not opened.

End-to-end verification

Two FerrisPad instances share one session. B's unsaved text must survive A's saves and a crash of B. Run from the branch's worktree with a throwaway config and data directory, so the run never reads or writes your real settings and sessions.

Starting state

  1. export XDG_CONFIG_HOME=$(mktemp -d) XDG_DATA_HOME=$(mktemp -d), then mkdir -p $XDG_CONFIG_HOME/ferrispad and write {"session_restore":"Full","tabs_enabled":true} to $XDG_CONFIG_HOME/ferrispad/settings.json No session exists yet: ls $XDG_DATA_HOME is empty.
  2. nix develop -c cargo build A debug build is in target/debug/FerrisPad.

The scenario

  1. Start A: target/debug/FerrisPad &. Press Ctrl+T and type "from A". A shows an unsaved "Untitled" tab.
  2. In the same shell, start B: target/debug/FerrisPad & echo $!, and note B's pid. Press Ctrl+T in B and type "from B". B has its own unsaved tab.
  3. Wait about 35 seconds for both auto-saves, then type " more" in A and wait again. $XDG_DATA_HOME/ferrispad/session/default/session.json lists both documents with different owner values, and both *.tmp files exist.
  4. kill -9 <B's pid>, then quit A with Ctrl+Q. If it asks about unsaved changes, choose Quit Without Saving: with Full restore, the session keeps the text. Before the fix, B's temp file was already gone at this point.
  5. Start one instance: target/debug/FerrisPad. Both "from A more" and "from B" come back as unsaved tabs.
  6. Close the "from B" tab and choose Discard. Quit, as in step 4, and start again. Only "from A more" comes back: the closed copy stays closed.
  7. rm -rf "$XDG_CONFIG_HOME" "$XDG_DATA_HOME" The throwaway dirs are gone.
