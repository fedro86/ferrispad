A syntax-highlighting update repaints only the text it restyled, not the whole editor

Before · On an 8 MB one-line file, one typed key took about 2 s longer with highlighting on than off. Opening an 8 MB multi-line file spent about a quarter of its time repainting the whole editor after every 64 KiB chunk.
After · A keystroke's re-highlight and each chunk repaint only their own range. One key on the 8 MB line costs 39 % fewer instructions, and the chunked open costs 45 % fewer. The colours on screen are pixel-identical.

This follows T0087's known limitation. The orchestrator reserved the ticket for 0.9.11, stacked on T0096. Every highlight write called redraw(). FLTK answers that with FL_DAMAGE_ALL, which runs recalc_display() twice, and each call re-measures the whole buffer. The change only does less work on user actions, so the 0% idle CPU rule is untouched.

  • One rule, HighlightController::show_restyle, serves every partial style write of the active document.
  • The style table is re-bound only when it gained entries. Only the restyled range is repainted, with redisplay_range.
  • The 64 KiB chunk overhead that T0087 accepted is won back in instructions: the open now takes 17 % fewer instructions than at 256 KiB before. In the single, noisy wall-time pass it is not yet at parity: 6.8 s at 64 KiB after this change, against 6.0 s at 256 KiB.

T0095: a restyle repaints only the restyled range

Before · Every keystroke's re-highlight, and every chunk of the background highlight, re-bound the style table and called redraw() on the whole editor.
After · show_restyle re-binds the table only when it gained entries, then calls redisplay_range on the range it restyled. apply_incremental (a keystroke step, or a T0096 continuation step) and each chunk step of continue_chunked_highlight go through it. T0096's full_repaint flag is gone.

FLTK's own recipe for a style-buffer update is redisplay_range (test/editor.cxx, style_update). It sets FL_DAMAGE_SCROLL and draws only that range. Every style-table entry uses the same font, so a restyle never changes glyph widths or wrap points.

  • Unchanged: whole-buffer style writes, which happen once per action and keep their full repaint. These are a full highlight, Re-highlight All, a theme or font change, and plugin line annotations.
  • Unchanged: the 64 KiB chunk size.

No visible change: the repaint covers less area but draws the same colours. pix95.sh (compare -metric AE, before against after) found 0 differing pixels on each of five screenshots:

  • a Rust file after open;
  • the same file after typing /* x, which turns the rest of the screen into a comment;
  • after closing the comment with */;
  • the 8 MB multi-line file at the top while chunking runs;
  • the same file at the end, after the chunked pass.

Each screenshot was also inspected. Those runs predate the new-pr skill.

The defect, red first. tests/restyle_damage.rs builds the real main window and AppState. On T0096's tip (23190d2) it failed:
  • "a keystroke's re-highlight repainted the whole editor: Damage(Expose | All)";
  • "a keystroke's re-highlight repainted no range: Damage(Expose | All)";
  • "26 of 27 chunk steps repainted the whole editor".
Why not skip identical style writes. On the 8 MB line, comparing the new style bytes with the current ones would copy the same 8 MB out of the style buffer that the write moves. After this change the remaining repaint covers only the visible part of the range, so the skip would save little and add a branch.
Seen in the screenshots, fixed elsewhere. The line-number gutter cut 5-digit numbers the same way before and after. That was T0107's bug, now on master through #197.

End-to-end verification

A user opens a large source file with highlighting on, types in it and scrolls while it is still being highlighted. Run from the branch's worktree with a throwaway config and data directory, so the run never reads or writes your real settings and sessions.

Starting state

  1. S=$(mktemp -d) && export XDG_CONFIG_HOME=$S/cfg XDG_DATA_HOME=$S/data, and for i in $(seq 1 40); do cat src/app/controllers/highlight.rs; done > $S/big.rs ls -l $S/big.rs shows a file of several MB.
  2. nix develop -c cargo run --release -- $S/big.rs The file opens with highlighting, and the "highlighting…" banner shows while the background pass runs.

The scenario

  1. While the banner is shown, scroll down with PageDown. The colours fill in as the pass advances, with no flicker of the whole editor.
  2. Go to the middle of the file (Ctrl+G, a line number) and type /* x. The rest of the screen turns into a comment.
  3. Type */, then pause. The colours return to normal, with no stale comment colour left.
  4. Quit without saving, then rm -rf "$S". The throwaway dir is gone.

The gates

  1. nix develop -c cargo test, nix develop -c cargo clippy --all-targets --all-features -- -D warnings, nix develop -c cargo fmt --check all green, zero warnings.
