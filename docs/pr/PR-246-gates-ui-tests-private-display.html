The gates run the UI tests on a private display, never on your screen

Before · At every commit, from any session, the pre-commit hook ran cargo test with your desktop's display. The UI tests build real FerrisPad windows and dialogs, and they could flash on your screen.
After · One script, scripts/gates.sh, runs the gates. The tests get an Xvfb of their own, as in CI. Your DISPLAY, your Wayland socket and your session bus never reach them, and the tests check that FLTK really opened that private display. The hook and every doc that lists the gates use it.

ferrispad-39 found this on 2026-11-27, while preparing T0108's UI tests. From the VSCode Flatpak sandbox, the gates go through flatpak-spawn --host. That host shell has DISPLAY=:0 and WAYLAND_DISPLAY=wayland-0, so display_available() saw a display and ran the UI tests on it. This is the same class of leak as the file dialogs that reached your GNOME session on 2026-11-27. The orchestrator (ferrispad-03) set the scope.

  • scripts/gates.sh: fmt, clippy -D warnings, then cargo test under xvfb-run -a, without your DISPLAY, WAYLAND_* or session bus, with FLTK_BACKEND=x11, a private XDG_RUNTIME_DIR and FERRISPAD_REQUIRE_UI_TESTS=1.
  • Under that variable the UI tests assert that the X display FLTK opened is the private one, never :0 or :1.
  • The pre-commit hook calls it, and a new hook test pins the environment the tests get.

How a gate run works, now

Hook · On git commit, .claude/hooks/pre-commit-gates.sh finds the checkout and runs the gate script that ships next to it: through flatpak-spawn --host from the sandbox, or directly on the host.
Lint · nix develop --command: cargo fmt --check, then cargo clippy --all-targets --all-features -- -D warnings.
Tests · env -u DISPLAY -u WAYLAND_DISPLAY -u WAYLAND_SOCKET -u DBUS_SESSION_BUS_ADDRESS FLTK_BACKEND=x11 XDG_RUNTIME_DIR=<private> FERRISPAD_REQUIRE_UI_TESTS=1 xvfb-run -a nix develop --command bash -c 'cargo test'. A missing display fails the gate instead of skipping the UI tests.
Proof · Each UI test binary, once the display is open, asserts that FLTK is not on Wayland and that the X display it opened (XDisplayString(fltk::app::display())) is $DISPLAY, not :0 or :1. It prints that display, for example FLTK on the private X display :99.

T0122: one gate script, tests on a private display

Before · The hook ran nix develop --command bash -c 'cargo fmt --check && cargo clippy … && cargo test' in the host's environment. The docs listed three bare nix develop -c cargo … commands, which, run from the host shell, behave the same way.
After · scripts/gates.sh [<checkout>] is the gate. Its tests run like CI's xvfb-run -a cargo test, and the docs tell sessions not to run a bare cargo test from the host shell as a gate.
  • The hook uses its own copy of the script (the main checkout's), so a worktree on an older branch is gated the same way.
  • Test seams: FERRISPAD_GATES_CMD stands in for the cargo gates, as before, but now runs inside the private-display environment. FERRISPAD_GATES_XVFB stands in for xvfb-run -a.
  • Not changed, by the orchestrator's decision: display_available(). If you run cargo test on your own desktop on purpose, the UI tests still run there.

No visible change: a process change (a script, the commit hook, docs). FerrisPad itself is untouched. What changes is what you no longer see: no test window on your screen when a session commits.

The review's catch, red first. ferrispad-90 found that removing WAYLAND_DISPLAY is not enough. fltk is built with use-wayland. Where that backend is compiled in, FLTK calls wl_display_connect(NULL) first when FLTK_BACKEND is unset, and libwayland then falls back to wayland-0 in XDG_RUNTIME_DIR: your compositor. Case 15 now also checks FLTK_BACKEND=x11, an XDG_RUNTIME_DIR that is not the caller's, and no session bus. On e86b8c0: 
FAIL 15. FLTK is forced onto X11: '^FLTK_BACKEND=x11$' is absent in the gate's environment
FAIL 15. the gate does not see the caller's XDG_RUNTIME_DIR: '^XDG_RUNTIME_DIR=/run/user/4242$' is present in the gate's environment
FAIL 15. the gate does not see the caller's session bus: '^DBUS_SESSION_BUS_ADDRESS=' is present in the gate's environment
24 passed, 3 failed
After the fix: 27 passed, 0 failed.
Why keep the tests and pin the display. Skipping the UI tests locally would hide a layout regression until CI. Running them on a private Xvfb keeps them. The assertion on the display FLTK really opened turns "the environment looks right" into "FLTK used it". It has no safe red run: its failure case is opening your :0 or :1, and both belong to your session here.
Open question: no Wayland in the local build. Cargo.toml asks for use-wayland, and cargo enables it on fltk-sys. Yet the local FLTK has /* #undef FLTK_USE_WAYLAND */ in fl_config.h, the CMake cache has no FLTK_BACKEND_WAYLAND, and ldd shows no libwayland-client (ferrispad-90). So here the leak went only through DISPLAY=:0 (XWayland). Whether release builds get Wayland, and should, may be a packaging question for its own ticket.
Until this lands. Master's hook still runs the UI tests on your display at every commit of every session. Sessions cannot avoid it without bypassing the hook, which the rules forbid. For manual gate runs they already use the safe form. Also, xvfb-run -a picks its display by testing lock files, so it can collide with a concurrent Xvfb. That makes the gate fail, never leak; a rerun fixes it.
