compare.sh and shoot.sh runs are safe to run concurrently

Before · Two sessions taking screenshots at the same time could break each other. One compare.sh run deleted the "before" build another run was using. Two shoot.sh runs could share one virtual display, and one run then typed into the other run's FerrisPad.
After · Each compare.sh run builds "before" in a worktree of its own. Each shoot.sh run reserves its display atomically and refuses any X server it did not start. Parallel sessions can open PRs with screenshots at once.

The reviewer (ferrispad-90) hit the compare.sh race on 2026-11-27 while reviewing PR #215 next to another session's run. ferrispad-3b found the display race the same day: two runs got :91. The orchestrator (ferrispad-03) put both in one ticket, since they are the same class of bug: tool runs that are not safe concurrently.

  • compare.sh: a mktemp worktree per run, removed only by that run; a shared cargo target under flock.
  • shoot.sh: the display is reserved with flock, and the X server must be the run's own Xvfb.
  • The selftest has three new checks; the new-pr skill says concurrent runs are safe.

How a run keeps to itself, now

compare.sh · "before" is built in ferrispad-wt/compare-<sha>.XXXXXX, never an existing directory. Under flock compare-target.lock it builds with the shared CARGO_TARGET_DIR=ferrispad-wt/compare-target, copies the binary into its own worktree, and cleans the FerrisPad crate. Its trap removes only its own worktree.
shoot.sh, outer half · Takes :N only with flock -n /tmp/ferrispad-shoot-display-N.lock, and only if :N has no X lock or socket. xvfb-run and Xvfb keep the lock, so the kernel frees it when the run ends, even on kill -9.
shoot.sh, inner half · Refuses to run unless the X server on DISPLAY (the pid in /tmp/.X<n>-lock) is a child of its own xvfb-run.

T0120: concurrent screenshot runs

Before · compare.sh used one fixed path per base sha, compare-<sha>, and reused it if it existed. shoot.sh checked that :N was free and only then started Xvfb on it.
After · No path and no display is shared between two runs, and a run that would land on someone else's X server stops instead.

No visible change: the screenshot tools only. FerrisPad and its tests are untouched. The montages these tools make look the same; what changes is that two of them can be made at once.

In case 3, B's Xvfb never started. xvfb-run still ran B's scenario on A's server, so B's Ctrl+F opened the Find dialog in A's app.
Why a lock plus an ownership check. The flock makes two shoot.sh runs pick different displays. Other X servers (CI's xvfb-run -a, a stray Xvfb) do not take that lock. The ownership check covers them: whatever happens, a run never drives a server it did not start. The check walks the process tree only up to the run's own outer shell. A first version walked to pid 1 and accepted a stranger's Xvfb, because systemd --user is everyone's ancestor. The new selftest check caught that.
The shared target. ferrispad-wt/compare-target/ stays between runs (890 MB of dependencies), so a run does not rebuild them all. It holds no FerrisPad artifacts after a run, so it does not grow with each run. Old compare-<sha> directories that earlier runs left behind are not cleaned up here.
