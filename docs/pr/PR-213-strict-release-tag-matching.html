Only a real version tag starts, signs or publishes a release

Before · Pushing a tag such as vandal, 1.2.3- or 01.2.3 started a release build. CI signed it with the release key, published it as a GitHub release and notified FlatPark.
After · Only X.Y.Z and X.Y.Z-(alpha|beta|rc).N, with no leading zeros, can publish. The release workflow and bump-version.sh share one regex, and a test checks that both copies are the same string.

a3 found the gap while reviewing T0086, and the orchestrator reserved the ticket for 0.9.11. The release workflow decided what a version tag is in two places, and bump-version.sh in a third. All three accepted names that are not versions in this repo's convention. Every existing tag follows that convention.

  • One strict rule: ^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)(-(alpha|beta|rc)\.(0|[1-9][0-9]*))?$.
  • The release-gate job and bump-version.sh use exactly that string.
  • The tag triggers are four globs. They pre-filter the runs; the gate decides what gets published.
  • RELEASE_PROCESS.md states the convention and where it is enforced.

Where a tag is checked, now

Trigger · on.push.tags has four filters: [0-9]+.[0-9]+.[0-9]+, and the same with -alpha.[0-9]+, -beta.[0-9]+ or -rc.[0-9]+. v* and X.Y.Z-* are gone. GitHub filters are globs, so they cannot rule out leading zeros.
Gate · release-gate matches the strict regex. Only then do sign-binaries, create-release and flatpark run. Otherwise the run builds only.
Bump · scripts/bump-version.sh refuses any other version before it changes a file.

T0111: one strict rule for a release version

Before · The gate's regex was ^(v[^/]*|[0-9]+\.[0-9]+\.[0-9]+(-[^/]*)?)$. It would have signed and published 15 of 19 non-versions.
After · The gate and the bump script accept exactly the convention. The triggers accept every valid version and none of v*, 1.2.3-, 1.2.3-foo.1 or 1.2.3-rc.

tests/release_tags.rs reads the gate regex, the bump-script regex and the trigger globs from the files themselves. It checks a table of 26 tag names against all three. glob_semantics pins the glob translation on GitHub's documented examples.
