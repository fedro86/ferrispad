A written procedure for fixing security defects privately

Before · "Fix privately, disclose with the release" lived only in the user's instructions to the sessions. Each session had to be told again what private means, and a session that started after a reset did not know it.
After · The rule .claude/rules/security-fixes.md loads in every session. It says where a finding goes, what may be pushed (nothing, until the release), and how it becomes public.

The user asked on 2026-11-28 to standardise the procedure used so far. They chose the local-only flow: GitHub Security Advisories with a temporary private fork were rejected, because status checks do not run there. The rule is generic process text: it names no finding and gives no exploit detail.

  • Triage: input someone else can shape that crosses a trust boundary is a security defect; an ordinary local crash stays a public bugfix.
  • Private workspace: gitignored docs/internal/security/S<N>-*.md tickets, local sec/ branches with no upstream, append-only merge notes, wording that names the area and not the exploit.
  • Work loop: red test first, scripts/gates.sh, private compare.sh scenarios, review by message, a blind recipe with throwaway XDG directories, and an integration dry run before the release.
  • Disclosure with the release: the first push of a fix starts the disclosure, so it happens in the release window, in one sitting: each fix as one commit on a fresh ticket/ branch, its issue and PR, CI, merge; then the CHANGELOG ### Security section and the SECURITY.md row on master; then the tag.
  • One pointer each in CLAUDE.md and work-sequence.md.

How a security finding travels, now

Found · Triage says private: an S ticket in docs/internal/security/, gitignored, with the next S number.
Fixed · A local sec/<slug> branch, red test first, the gates, a local review by message, the user's blind check.
Released · In the release window, in one sitting: a T ticket, one commit, an issue and a PR for each fix, merged in the dry run's order; the CHANGELOG Security section on master; then the tag.

T0123: the security-fix procedure

Before · The procedure existed only as instructions repeated to each session.
After · It is a binding rule in .claude/rules/, next to work-sequence.md and engineering-standards.md.

The rule records the flow as it was actually used. It also writes down the lessons that came with it: merge notes are appended, never rewritten; a red test that must be committed before its fix is marked #[ignore], because the pre-commit hook refuses a failing test; and two fixes must not escape the same text twice.

No visible change: process text only. FerrisPad's code is untouched.

Why the S tickets live outside git. docs/internal/ is gitignored, so a private ticket cannot reach a commit by accident: git check-ignore proves it. The T ID is taken only at disclosure, so no public number is reserved where other sessions cannot see it.
The user's call, not changed here. SECURITY.md "Reporting Vulnerabilities" still has [security contact to be added], and GitHub private vulnerability reporting is off. Turning it on would give reporters a private channel.
