How a PR goes out, now

1 · Number · gh pr create --draft gives the PR number. It is never guessed.
2 · See it · compare.sh <scenario> builds the base ref and the branch, runs the scenario on both in an isolated Xvfb (light and dark), and writes before | after montages. Every shot is read edge by edge.
3 · Page · docs/pr/PR-<n>-<slug>.html from the template, facts only. The ticket card is the heart of the page.
4 · Copy · The page is copied to the main checkout's docs/internal/pr/ (gitignored) for the user, again after every fix.
5–6 · Commit, hand over · The page is committed on its own. The PR body is one paragraph, the page's path and Closes #<issue>. The PR stays a draft while the user verifies. It goes ready together with the move of the ticket to 3-done/.
7 · Merge · Only when all five conditions hold:
  • the visual check has passed;
  • the user's feedback is addressed;
  • the ticket is in 3-done/ and the PR is no longer a draft;
  • every check is green on the head SHA;
  • the user has given explicit consent for this PR.
The merge uses gh pr merge --squash --match-head-commit.
8 · After · Any session that sees the PR merged or closed deletes the copy. The page is never moved.

FerrisPad itself does not change. What changes is that a session can now see it. Below is what compare.sh produced on its first real case, T0114's start page, comparing 0.9.10-rc.2 with this branch. It is the montage the README's worked example uses.

Incident: file dialogs on the user's real desktop. I was debugging an early open_file helper (Ctrl+O, then type a path). The nix-built FerrisPad found no loadable GTK, so its file chooser was zenity, spawned as a child. zenity escaped Xvfb through the user's session (D-Bus and the Wayland socket): every debug run left an "Open Files" dialog on the user's GNOME desktop. The orchestrator stopped the runs, and I killed the 8 orphaned zenity shells. shoot.sh now refuses to start without these barriers:
  • a private D-Bus with no service activation;
  • a private, empty XDG_RUNTIME_DIR with GDK_BACKEND=x11;
  • a DISPLAY that must be its own Xvfb, never :0/:1;
  • shims for zenity, xdg-open and the other openers (any call fails the run);
  • no update checks;
  • fixtures opened on the command line, and key refusing Ctrl+O and Ctrl+S;
  • its process group killed at the end.
Review round 3 added more barriers:
  • the app's whole environment is an env -i allowlist, with its own HOME, cwd, TMPDIR and SHELL=/bin/sh;
  • a per-run marker in /proc/*/environ catches any process that left the group.
shoot.sh --selftest checks all of them without starting FerrisPad: 18/18 ok. The guard refuses the user's bus, a missing bus and DISPLAY=:0. Every run since has left nothing on the host.
Why the Playwright headless shell (the minor page check). No Chromium is on the sandbox's PATH or in the nix profile. ~/.cache/ms-playwright/chromium_headless_shell-1248 runs inside the Flatpak sandbox, so the check needs no flatpak-spawn. Its dark mode is --blink-settings=preferredColorScheme=0. --force-dark-mode was tried and dropped: it leaves prefers-color-scheme light in the headless shell, tested on a probe page.
Why a probe copy. The page carries no script. visual_check.sh puts the measuring script into a copy in the output folder, reads the result from --dump-dom, and screenshots the untouched page at its full height.
The annotation-only exemption is narrow. A PR needs no page only if every line of git diff --name-status origin/master...HEAD is M docs/tickets/3-done/… or A docs/tickets/1-todo/…, as in #230 and #233. a3 asked to narrow it in review, and the orchestrator decided to. Anything else gets a page: a ticket move, an edit to an open ticket, a deletion, the ticket template.
Found in review round 3, fixed. compare.sh piped cargo into tail. So if the branch's build failed, the old binary was used and the montage labelled it with HEAD's SHA. The build now keeps cargo's status and refuses a binary older than its sources. A deliberately broken worktree makes compare.sh exit 1 with no montage.
Found in review, fixed. The first version of §6 marked the PR ready before the user verified it, against work-sequence.md step 3. The draft flag would then have stopped meaning "waiting for the user". Now the PR goes ready only with the 3-done/ move. a3 also found that visual_check.sh would have passed four light renders if Chromium ignored the color-scheme flag. It now fails closed: a test wrapper that drops --blink-settings makes it exit 1.

End-to-end verification

Walk the next PR through the skill, from the draft to the copy the user reads. Use this PR as the model.

Starting state

  1. A ticket in 2-review/ on its pushed ticket/T<NNNN> branch, with origin/master merged in and the gates green. git status is clean and git log origin/master..HEAD shows the ticket's commits.

The scenario

  1. Run §1: gh pr create --draft …, then gh pr view ticket/T<NNNN> --json number. a draft PR exists, and its number names the page.
  2. Run §2 on a UI change: write docs/pr/scenarios/<ui>.sh, then compare.sh it, with --font 18 too. <shot>-light-compare.png and -dark-compare.png, each read edge by edge; the host stays clean.
  3. Run §3 and §4: write the page from the template, then copy it to docs/internal/pr/. the page opens in a browser from the main checkout, with the figures in the ticket card.
  4. Run §7 condition 1: visual_check.sh. four ok lines.

The gates

  1. nix develop -c cargo test, nix develop -c cargo clippy --all-targets --all-features -- -D warnings, nix develop -c cargo fmt --check all green, zero warnings: no Rust file changes.
