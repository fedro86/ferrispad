A long file path with non-ASCII characters never crashes the status bar

Before · Open a file whose path holds non-ASCII characters (é, ß, Japanese…) and make the window narrower than the path: at some width FerrisPad panics and quits, losing any unsaved work.
After · The path in the status bar shortens from the left ("…/rest" or "…name") at every width, and "Ln X, Col Y" stays in view, also with a Japanese file name.

Found while reading src/ui/status_bar.rs: it shortened the path by slicing it at a byte offset, &self.path_text[skip..]. An offset inside a multi-byte character panics. The engineering standards forbid exactly this ("no raw slicing of &str by byte offsets without a char-boundary guard").

  • The path is measured and cut in display columns, between characters, never at a byte offset.
  • A CJK or fullwidth character counts as two columns, as it is drawn about twice as wide as an ASCII one, so "Ln X, Col Y" keeps its place.
  • No change for ASCII paths.

T0124: the status bar shortens any path safely

Before · A non-ASCII path, in a window narrower than it, could crash FerrisPad.
After · The path shortens; the editor keeps running; "Ln X, Col Y" stays visible.

Shots from compare.sh with the new scenario docs/pr/scenarios/status-bar-path.sh: the fixture's name is mostly Japanese, and the window narrows from 900 to 580 px, one shot per width. Before = master 62669e9, after = this branch.

Master crashes. At 760 px, in light and dark, the app exits and shoot.sh stops the run: thread 'main' panicked at src/ui/status_bar.rs:159:59: start byte index 5 is not a char boundary; it is inside 'モ' (bytes 3..6 of string). So master has shots at 900 and 820 px only.

The after shots at 900, 820, 700 and 640 px, light and dark, were read too: the name and "Ln 2, Col 1" are whole at every width.

Two defects, red first. long_non_ascii_path_never_panics tries every width for a German and Japanese path. On the byte-based code it failed: start byte index 90 is not a char boundary; it is inside 'モ'. Then, in the app, counting characters let a Japanese name push "Ln X, Col Y" off the bar. ln_col_stays_inside_the_bar_with_a_cjk_path failed: 42 columns in a 36-column bar.
Why columns, and not a font measure. The bar already lays out by an average character width (7 px) and pads with spaces. Counting a wide character as two columns fits that model with no new dependency and no drawing context. Measuring with the font would mean redoing the bar's layout, which this fix leaves alone.
