An official plugin's shortcut can no longer clash with a core one unnoticed

Before · Rust Lint 1.5.0 advertised Ctrl+Shift+R for Run All Checks. That key is File → Reload All, so the plugin's binding was always skipped, and every start logged a warning. Nothing in this repo noticed.
After · Rust Lint 1.5.1 (ferrispad-plugins#1) declares no shortcut. Its checks run on Ctrl+Shift+L, Plugins → General → Run All Checks. A unit test binds every official plugin's shortcuts against the core ones and fails on a clash.

The warning was seen on 2026-11-07, while T0072 was verified by hand. Core's policy is right: core keeps its key and the plugin binding is skipped. The defect was the shipped manifest. The user chose to drop the shortcut rather than pick another key. This PR adds the guard; the manifest fix is in the plugin repo.

  • plugin_shortcut_conflicts: the five official manifests are bound through the runtime's own PluginShortcutBinder. A clash fails the test and names who holds the key.
  • builtin_shortcuts_are_reserved: every core default shortcut is in the binder's hand-kept RESERVED_SHORTCUTS, in both tab modes.
  • The manifests are verbatim copies in tests/fixtures/official_plugins/, with a README saying where they come from.

T0073: the Ctrl+Shift+R clash, and a guard against the next one

Before · With Rust Lint 1.5.0 installed, every start printed [plugins] Warning: shortcut 'Ctrl+Shift+R' for Rust Lint/Run All Checks conflicts with existing shortcut, skipping. The plugin's README promised a key that never worked.
After · Rust Lint 1.5.1 has no shortcut on Run All Checks, and its README points to Ctrl+Shift+L and Edit → Key Shortcuts. With all five official plugins installed, the start log has no shortcut warning. File → Reload All keeps Ctrl+Shift+R.

The user's decision, relayed by the orchestrator: drop the shortcut. Core Ctrl+Shift+L fires on_highlight_request, which in Rust Lint calls the same run_all_checks as the menu item, so nothing is lost. A user who wants a dedicated key can set one in Edit → Key Shortcuts.

  • The plugin repo: ferrispad-plugins#1 (adb75f5) removes the shortcut, bumps Rust Lint to 1.5.1, and updates its README and CHANGELOG.
  • The other official plugins: file-explorer Ctrl+Shift+E, git-diff Ctrl+Shift+D, python-lint Ctrl+Shift+P, yaml-json-viewer Ctrl+Shift+Y. None of them clashes.
  • The fixtures are current: rust-lint is byte-identical to PR #1's head, and the other four to the plugin repo's main (checked 2026-11-27).

No visible change: this PR adds tests and fixtures only, and the FerrisPad binary is the same as master's. The change a user sees, the Rust Lint menu and the quiet start log, ships with the plugin update.

Pending user, now that Rust Lint 1.5.1 is published: update Rust Lint in the Plugin Manager and restart. Look for no shortcut warning in the log and no shortcut next to Plugins → Rust Lint → Run All Checks. Ctrl+Shift+R must still reload all files.

The defect, red first. With the Rust Lint 1.5.0 manifest (plugin repo cce6006) as the fixture, the guard failed: 
thread 'ui::menu::tests::plugin_shortcut_conflicts' panicked at src/ui/menu.rs:909:9:
Rust Lint/Run All Checks (Ctrl+Shift+R) clashes with File/Reload All
With the 1.5.1 manifest it passes. builtin_shortcuts_are_reserved passes before and after: it guards against drift.
Why bind through the runtime's binder. The test uses the same PluginShortcutBinder as the Plugins menu: reserved core keys first, then earlier plugin items. A separate table in the test could drift from what the app really does.
Published. On the user's OK (2026-11-27), ferrispad-plugins#1 was merged as 017442d, and the auto-sign bot signed Rust Lint 1.5.1 in fd7a6a4, which touched only plugins.json. All five fixtures are byte-identical to main at fd7a6a4.
